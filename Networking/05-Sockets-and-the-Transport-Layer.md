# Chapter 5: Sockets and the Transport Layer

## 1. What this chapter is actually for

Chapter 4 closed its worked example at the exact moment a SYN and SYN-ACK crossed a NAT gateway, deliberately leaving TCP's own internal behavior as something to take on faith. This chapter cashes that in: what TCP and UDP actually do, as kernel-resident state machines, to turn IP's best-effort, unordered, unreliable packet delivery into the reliable byte stream (or, for UDP, the simple datagram service) that the socket API exposes to an application.

Chapter 1 already introduced the socket API surface and TCP's named states as observable facts. This chapter goes underneath that surface: how a `struct sock` actually tracks a connection's buffers, how retransmission timers are chosen, what congestion control is actually protecting against, and why certain socket options change behavior in ways that surprise people who've only seen them listed in a manpage without the underlying mechanism to explain them.

It's worth naming, up front, why this particular chapter tends to reward closer attention than some of the others in this series: TCP's reliability and congestion-control machinery is where a genuinely large fraction of "why is this connection slow" and "why does this application behave differently on this network than on that one" questions ultimately get answered. Chapters 2 through 4 covered mechanisms that are mostly either working correctly and invisibly, or visibly broken in ways that produce clear symptoms (a dropped interface, a misrouted packet, a firewall rule blocking the wrong thing). TCP's behavior is different in kind: it is *designed* to adapt continuously to whatever conditions it measures, which means its behavior on a given connection is rarely simply "correct" or "broken" — it's usually doing exactly what its algorithms say it should, given the conditions it has actually observed, and understanding whether that behavior is *appropriate* for a given situation requires understanding the algorithms themselves, not just recognizing an error state.

## 2. The socket buffer model: send and receive queues as real, bounded memory

Chapter 1, section 4, described `write()` as copying bytes into "the socket's send buffer" without saying much about what that buffer actually is. It's worth being precise now: every TCP socket maintains two genuinely separate, bounded queues of `sk_buff`s (chapter 2's structure, reused here for exactly the reason chapter 2 argued it exists — the same buffer format serves every layer) — a send queue, holding data written by the application that hasn't yet been fully acknowledged by the peer, and a receive queue, holding data that has arrived from the peer but not yet been consumed by the application's `read()` calls.

### 2.1 Why the send buffer isn't just "in-flight data"

It's tempting to think of the send buffer as simply "data currently on the wire," but it holds more than that: TCP must retain a copy of every byte it has transmitted until that byte is acknowledged, specifically so it can retransmit if the acknowledgment never arrives. This means the send buffer's occupied size at any moment reflects both data genuinely in flight *and* data the kernel has already handed to the driver but is keeping a copy of purely as insurance against loss. A `write()` call can block (or, for a non-blocking socket, return `EAGAIN`) not because the network is slow in some abstract sense, but concretely because this buffer is full — every byte in it is either unacknowledged or waiting for room to be transmitted, and until the peer's acknowledgments free up space by confirming earlier bytes, there's genuinely nowhere to put more.

### 2.2 Why the receive buffer size determines the receive window

The receive buffer's available free space is precisely what TCP advertises to the peer as its **receive window** — the field in every TCP segment's header telling the sender how many more bytes it may send before waiting for the receiver to catch up. This is directly why receive buffer size is a genuine performance lever, not just a memory-tuning knob: a small receive buffer caps the window small, which caps how much data the sender can have in flight at once, which — on a network with meaningful round-trip latency — caps achievable throughput regardless of how fast the underlying link actually is, because the sender can't send more until acknowledgments (which only arrive after a full round trip) free up window again. This relationship, throughput bounded by window size divided by round-trip time, is worth internalizing as a formula precisely because it explains a specific, common real-world symptom: a connection that performs fine on a low-latency local network but disappointingly on a high-latency long-distance link, even though the link's raw bandwidth is more than sufficient — the window, not the link, is the bottleneck, and it's fixable by increasing buffer sizes (`net.core.rmem_max`/`net.ipv4.tcp_rmem`) to allow a larger window for exactly these high-latency paths.

```
$ ss -tin
State  Recv-Q  Send-Q  Local Address:Port    Peer Address:Port
ESTAB  0       0       192.168.1.42:51422   93.184.216.34:443
       cubic wscale:7,7 rto:204 rtt:2.847/1.2 mss:1448 cwnd:10
       bytes_sent:5821 bytes_acked:5822 bytes_received:142891
```

The `wscale:7,7` field is directly relevant here — it reflects the **window scaling** option, negotiated during the handshake, that lets TCP advertise a window larger than the header's native 16-bit field alone could express (a plain 16-bit window field maxes out at 65,535 bytes, hopelessly small for high-bandwidth, high-latency modern links — window scaling multiplies the advertised value by a negotiated power of two, extending the effective range considerably).

### 2.3 Autotuning: why manual buffer sizing is rarely needed today

It's worth noting that modern Linux kernels don't require an administrator to manually pick fixed buffer sizes for the common case — **socket buffer autotuning** dynamically adjusts a connection's send and receive buffer sizes within configured minimum/default/maximum bounds (`net.ipv4.tcp_rmem` and `net.ipv4.tcp_wmem`, each a three-value tuple), based on observed conditions for that specific connection: available system memory, the connection's measured round-trip time, and its actual observed throughput. This exists precisely because a single fixed buffer size can't be simultaneously correct for both a low-latency local connection (which needs comparatively little buffer to sustain full throughput, per section 2.2's window/RTT relationship) and a high-latency long-distance connection on the same machine (which needs considerably more buffer to avoid being window-limited) — autotuning lets each connection converge toward roughly the buffer size it actually needs, rather than forcing every connection on a machine to share one compromise value that's suboptimal for most of them. Manual tuning of the fixed bounds is still occasionally warranted — a machine specifically dedicated to very high-bandwidth, very high-latency transfers (long-distance data replication being a common case) may need the *maximum* bound raised beyond conservative defaults, since autotuning can only grow a buffer within the configured ceiling, not past it — but for the overwhelming majority of workloads, autotuning removes the need to reason manually about buffer sizing that this section's underlying mechanism might otherwise seem to demand.

## 3. Retransmission: timers, not just acknowledgments



Chapter 1 described TCP's states without dwelling on what actually triggers a retransmission. The mechanism is a per-connection timer, the **retransmission timeout (RTO)**, and getting its value right is a genuinely subtle problem TCP has spent decades refining.

### 3.1 Why a fixed timeout doesn't work

A naive, fixed retransmission timeout — say, always waiting exactly one second before assuming a segment was lost — fails on both ends of the spectrum: too short, and it triggers wasteful, unnecessary retransmissions on a genuinely slow but otherwise healthy path (a transcontinental or satellite link with an inherently high round-trip time); too long, and it leaves a connection needlessly stalled after a genuine loss on a fast, low-latency local network, waiting far longer than necessary before recovering. The right timeout is a function of the *actual, currently-observed* round-trip time for this specific connection, which varies enormously across different network paths and even over the lifetime of a single connection as network conditions change.

### 3.2 The RTO calculation, and why it tracks variance, not just the average

TCP addresses this by continuously measuring round-trip time (from segments sent and their corresponding acknowledgments) and maintaining a smoothed estimate — commonly called SRTT (smoothed round-trip time) — updated with each new sample via an exponentially-weighted moving average, rather than being recalculated from scratch on every measurement (which would make the estimate too noisy) or fixed at a single initial measurement (which wouldn't adapt to changing conditions). Critically, TCP also tracks the *variance* in observed round-trip times, not just their average — a connection whose RTT bounces between 20ms and 200ms unpredictably needs a much larger safety margin in its timeout than one whose RTT sits consistently near 50ms, even if both happened to average to the same value. The RTO is set to the smoothed average plus a multiple of this tracked variance, precisely so that a connection on a jittery path (mobile networks being a common real-world example) doesn't trigger spurious retransmissions every time its RTT happens to spike above its own average, while a connection on a stable path can still recover from genuine loss quickly, without waiting an unnecessarily generous margin it doesn't need.

### 3.3 Fast retransmit: not waiting for the timer at all

The RTO timer is, in practice, TCP's fallback mechanism — the *usual* way loss is detected and recovered from is faster and doesn't involve waiting for a timeout at all. When a receiver gets a segment out of order (implying an earlier segment is missing), it immediately sends a duplicate acknowledgment for the last correctly-received in-order byte, rather than waiting to see if the missing segment eventually arrives. If the sender sees three duplicate acknowledgments in a row — a specific, deliberately conservative threshold chosen to distinguish "one segment genuinely got lost" from ordinary packet reordering (which chapter 2, section 6.1, already discussed as something the network can introduce legitimately, and which produces exactly one or two duplicate acknowledgments as a byproduct, not three) — it retransmits the missing segment immediately, without waiting for the RTO timer to expire at all. This mechanism, called **fast retransmit**, is why real-world TCP connections typically recover from an isolated lost packet within roughly one round trip, rather than waiting out a multi-hundred-millisecond timeout — the RTO timer exists specifically for the harder cases fast retransmit can't handle (a loss so severe that no subsequent segments arrive at all to trigger duplicate acknowledgments in the first place).

## 4. Flow control versus congestion control: two different problems solved by the same window mechanism

Section 2.2 described the receive window as flow control — protecting the *receiver* from being sent more data than it has buffer space to hold. It's worth being precise that this is a genuinely different problem from **congestion control**, which protects the *network path* between sender and receiver from being sent more data than it can actually carry, and TCP maintains a second, independent window — the **congestion window (cwnd)** — specifically for this second problem. The amount of data TCP will actually have in flight at any moment is the *smaller* of these two windows, and conflating them is a common source of confusing an application-side buffering problem with a network-capacity problem when diagnosing throughput issues.

### 4.1 Why the network needs protecting from the sender at all

It's worth being explicit about the failure mode congestion control exists to prevent, because it's not obvious from the receiver-protection framing of flow control. Every router and switch along a path has finite buffer space; if senders collectively offer more traffic than a shared link can carry, those buffers fill, and once full, routers must drop packets. Naively, one might expect TCP senders to simply notice dropped packets (via the retransmission mechanism from section 3) and retransmit, with the network settling into some equilibrium — but without deliberate restraint, this can spiral: retransmitted data adds to the very congestion that caused the original loss, and if enough senders behave this way simultaneously, the network can enter a state (historically observed and named **congestion collapse**) where an increasing fraction of the network's actual carried traffic is wasted retransmissions of data that will itself be dropped again, while genuinely new, useful data barely gets through at all. Congestion control exists specifically to make each TCP sender behave cooperatively enough, in aggregate with every other sender sharing the same paths, to avoid this collapse — treating packet loss (or, with more modern algorithms, other signals) as evidence the network is near its capacity, and backing off rather than continuing to add load to an already-strained path.

### 4.2 Slow start: probing for capacity cautiously

A new TCP connection has no information at all about how much capacity the path between sender and receiver can actually support — it could be a fast local link or a heavily congested, low-bandwidth path, and sending aggressively from the first packet risks immediately overwhelming whichever it turns out to be. **Slow start** addresses this by beginning with a small congestion window (historically a handful of segments, tunable, and generally larger by default on modern kernels than in TCP's earliest specifications) and roughly doubling it every round trip that passes without evidence of loss — an exponential growth that, despite the name "slow start," actually ramps up quite quickly in absolute terms once a few round trips have passed, precisely because doubling compounds fast. This continues until either loss is detected (at which point congestion avoidance, section 4.3, takes over) or the congestion window reaches a threshold value (`ssthresh`) carried over from a previous loss event on this same connection, if any.

### 4.3 Congestion avoidance: growing cautiously once near the edge

Once slow start's exponential growth is curtailed — either by hitting `ssthresh` or by an actual loss event — TCP shifts to **congestion avoidance**, growing the congestion window far more conservatively (classically, by roughly one segment per round trip, rather than doubling) on the reasoning that the connection is now believed to be operating near the actual capacity of its path, where aggressive growth risks tipping back into loss almost immediately. This is the origin of the classic "sawtooth" pattern visible in a congestion window plotted over time for a long-lived TCP connection under sustained load: window grows steadily, a loss event occurs, the window is cut back substantially (historically halved, under the classic algorithms), and gradual growth resumes from that lower point — a pattern that is, in a real sense, TCP continuously and deliberately probing for the edge of available capacity, backing off when it finds that edge, and creeping back toward it afterward.

### 4.4 Modern congestion control: CUBIC and BBR as different philosophies

The classic loss-based model in sections 4.2–4.3 (historically associated with algorithms named Tahoe, Reno, and their direct descendants) treats packet loss as the primary, essentially only, signal that the network is congested. **CUBIC**, the default congestion-control algorithm on modern Linux (visible in the `ss -tin` output from section 2.2 as `cubic`), refines this same loss-based philosophy — its window-growth function is a cubic (rather than purely linear) function of time since the last loss event, designed to grow more aggressively when further from the previously-known point of congestion and more cautiously as it approaches that point again, an attempt to combine faster recovery of available capacity with the same fundamental "loss means back off" signal classic algorithms use.

**BBR** (Bottleneck Bandwidth and Round-trip propagation time), a considerably more recent alternative also available in Linux, takes a genuinely different philosophical approach: rather than treating loss as the primary signal, it actively models the path's bandwidth and minimum round-trip time directly from measured data, and paces its sending rate based on that model rather than primarily reacting to loss after the fact. The practical motivation is a real limitation of pure loss-based approaches: on paths with large, deep buffers (a genuinely common characteristic of some modern network equipment, sometimes called "bufferbloat"), a loss-based algorithm can end up filling those large buffers considerably before any loss actually occurs, driving up queuing latency substantially in the process, even though the *link* itself isn't actually the bottleneck — the deep buffer is simply absorbing more and more data before finally signaling congestion via loss. BBR attempts to avoid this by inferring the point of genuine bottleneck saturation directly from bandwidth and RTT measurements, without needing to first fill available buffer space to the point of overflow.

Which algorithm a given connection uses is configurable (`net.ipv4.tcp_congestion_control`, or per-socket via `setsockopt` with `TCP_CONGESTION`), and it's worth knowing this is a genuine behavioral choice with real trade-offs rather than a purely cosmetic setting — different algorithms can produce meaningfully different throughput and latency characteristics on the same physical path, and the "best" choice depends on the specific network characteristics involved (BBR's advantages are most pronounced precisely on the bufferbloat-prone and higher-loss-but-not-actually-congested paths where classic loss-based algorithms tend to perform worst).

### 4.5 ECN: signaling congestion without dropping a packet at all

Sections 4.2 through 4.4 described congestion signals as either inferred from actual packet loss (classic algorithms, and CUBIC's baseline behavior) or inferred from bandwidth/RTT measurements without needing loss at all (BBR). There's a third mechanism worth knowing about, sitting partway between these: **Explicit Congestion Notification (ECN)**, which lets a router experiencing incipient congestion mark a packet's IP header directly, rather than dropping it, signaling "this path is getting congested" to the endpoints without needing to sacrifice the packet itself as the signal. A receiver seeing this mark echoes it back to the sender (via a TCP header flag on the next outgoing acknowledgment), and a sender receiving that echo reduces its congestion window in response — functionally similar to how it would react to inferred loss, but without an actual packet having to be discarded to trigger the reaction, and correspondingly without the retransmission delay a genuine loss event would otherwise cost. This requires router support along the entire path (not universal, though increasingly common on modern network equipment) and is negotiated during the TCP handshake, meaning a connection can only benefit from it when both endpoints and the intervening path all support it — when unsupported anywhere along the way, TCP falls back transparently to the loss-based signaling described earlier in this section, with no correctness impact, only a missed opportunity for the modest additional efficiency ECN can provide.

## 5. UDP: what's deliberately absent, and what that buys



Chapter 1 characterized UDP as lacking a connection state machine in the transport-layer sense. It's worth being precise about exactly what UDP's socket-level implementation does and doesn't do, because "UDP has no reliability" is often stated as if UDP were simply TCP with features removed, when it's more accurate to say UDP provides a genuinely different, minimal service that certain applications are specifically better served by.

### 5.1 What a UDP socket actually tracks

A UDP socket still has send and receive buffers (section 2's model applies, in simplified form), but nothing resembling the retransmission timers (section 3) or congestion window (section 4) — a `sendto()` call on a UDP socket, once the kernel has queued the datagram, considers its job done; there's no tracking of whether that datagram was ever acknowledged, because UDP has no acknowledgment mechanism at all. This means, concretely, that a UDP application wanting reliability (ordered delivery, retransmission of lost datagrams) has to build that logic itself, at the application layer — which is precisely what protocols like QUIC (which runs over UDP specifically to gain deployability advantages UDP has over raw IP, while implementing its own considerably more sophisticated reliability and congestion-control layer on top, largely reproducing much of what sections 3 and 4 described, just outside the kernel) and many real-time media and gaming protocols do, each tailoring the reliability tradeoffs to their specific application's needs rather than accepting TCP's one-size-fits-all approach.

### 5.2 Why some applications genuinely want this

It's worth being explicit about why UDP's minimalism is a feature rather than merely an omission, for the applications that choose it deliberately. Real-time audio or video benefits from a datagram that arrives late or out of order simply being discarded rather than triggering TCP-style retransmission and reordering-buffer delay — for a live voice call, a late-arriving retransmitted packet from three hundred milliseconds ago is worse than useless, since real-time playback has already moved past the point where it could be used, whereas TCP's insistence on in-order, complete delivery would force exactly this kind of unhelpful delay onto data whose usefulness has already expired by the time it can be delivered correctly. UDP's lack of any built-in ordering or retransmission guarantee is precisely what lets an application layer make its own, application-appropriate decision about what to do with a late or missing datagram — discard it, interpolate around it, or simply accept degraded quality — rather than having TCP's generic, one-size-fits-all reliability policy imposed on data for which that policy is actively counterproductive.

### 5.3 Datagram size and fragmentation

One further practical detail worth flagging: unlike TCP (which segments a byte stream into appropriately-sized pieces automatically, transparent to the application, as chapter 2's section 4.5 on GSO touched on from the implementation side), a UDP datagram is sent as a single unit matching exactly what the application handed to `sendto()`. If that unit exceeds the path's MTU (chapter 1, section 5.2), IP fragmentation — splitting one oversized packet into multiple IP-layer fragments, reassembled only at the final destination — becomes necessary, and fragmentation carries real costs worth knowing about: if any one fragment is lost, the *entire* original datagram is lost (there's no fragment-level retransmission — IP fragmentation predates, and is considerably cruder than, TCP's segment-level reliability), and many network paths and firewalls handle fragmented traffic poorly or block it outright, for reasons related to the additional complexity fragment reassembly introduces for stateful inspection. This is precisely why applications sending UDP datagrams over paths where MTU is uncertain generally keep individual datagrams conservatively small (comfortably under the smallest MTU likely to be encountered along any plausible path) rather than relying on fragmentation to handle oversized ones correctly.

## 6. Socket options that matter, and the mechanism behind each

Chapter 1's socket API introduction mentioned socket options only in passing. It's worth closing this chapter with a look at a small number of commonly-encountered options, specifically because knowing *why* each one does what it does — rather than only that it exists — is what lets a decision about whether to use it be made correctly rather than by habit or folklore.

### 6.1 `TCP_NODELAY`: disabling Nagle's algorithm

By default, TCP applies **Nagle's algorithm**, which delays sending small segments briefly, in hopes of coalescing them with additional data the application might write shortly afterward, into fewer, larger segments — a genuinely useful optimization for reducing the overhead of many tiny packets on networks where that overhead matters (this was a considerably more pressing concern on the slower links common when Nagle's algorithm was designed than it typically is today). The cost is added latency for applications that send small, latency-sensitive messages and expect each one to go out immediately — the algorithm's coalescing delay directly works against exactly this use case. `TCP_NODELAY` disables Nagle's algorithm for a given socket, and it's the standard choice for latency-sensitive protocols exchanging small messages (many RPC frameworks, interactive protocols, and low-latency trading systems set this by default) — but it's worth understanding that disabling it isn't free: a chatty application sending many small writes with `TCP_NODELAY` set will genuinely generate more, smaller packets on the wire than it would with Nagle's algorithm coalescing them, a real tradeoff between latency and packet-count efficiency, not merely a "faster" setting to always prefer without considering the traffic pattern involved.

### 6.2 `SO_REUSEPORT`: multiple sockets sharing one listening address

Ordinarily, only one socket can be bound to a given address and port combination for listening. `SO_REUSEPORT` relaxes this, allowing multiple independent sockets — typically one per worker process or thread in a multi-process server architecture — to all bind to the exact same address and port, with the kernel itself load-balancing incoming connections across them (using a hash of the connection's four-tuple, similar in spirit to the RSS/RFS mechanisms chapter 2's section 6 described for spreading packet processing across CPU cores, and for a related reason — this option specifically exists to let a multi-process server scale across cores without needing a single process to accept a connection and then hand it off to a worker via some other, more expensive inter-process mechanism). Before this option existed, common patterns for the same goal (multiple worker processes handling connections to one listening port) required either a single process accepting all connections and distributing them manually, or having all workers contend over one shared listening socket via `accept()` — both of which introduce either a bottleneck or contention that `SO_REUSEPORT`'s kernel-side load-balancing avoids entirely.

### 6.3 `SO_LINGER` and the cost of getting connection teardown wrong

`close()` on a TCP socket, by default, returns immediately from the application's perspective, while the kernel handles the actual FIN/ACK exchange (and, if applicable, the `TIME_WAIT` period from chapter 1, section 8) in the background, asynchronously to the calling process. `SO_LINGER`, when enabled with a nonzero timeout, changes this: `close()` instead blocks until either all pending data has been successfully sent and acknowledged, or the specified timeout elapses — and, critically, `SO_LINGER` with a *zero* timeout changes the teardown itself, causing the kernel to abandon the connection immediately with a `RST` (a reset) rather than performing the ordinary graceful FIN-based close at all, discarding any unsent buffered data in the process. This last variant is occasionally reached for as a way to "force-close" a stuck connection quickly, but it's worth understanding the real cost: an abrupt RST-based teardown gives no assurance whatsoever that data the application believed it had successfully sent was actually received and processed by the peer, which is a meaningfully different (and generally worse) guarantee than the ordinary graceful close provides, and reaching for zero-timeout `SO_LINGER` as a routine pattern rather than a genuine emergency measure is a common source of silent data loss that's difficult to diagnose after the fact, precisely because nothing about it produces an obvious error on the sending side.

### 6.4 `SO_RCVBUF`/`SO_SNDBUF`: manually overriding autotuning

Section 2.3 described autotuning as the default, generally-sufficient mechanism for sizing a connection's buffers. `SO_RCVBUF` and `SO_SNDBUF` let an application override this on a per-socket basis, setting a fixed buffer size directly rather than allowing the kernel's autotuning to adjust it dynamically. This is occasionally the right choice for a specialized application with unusual, well-understood traffic characteristics (a media server handling many concurrent connections, each transferring a broadly predictable amount of data, might deliberately cap per-socket buffer size to bound aggregate memory consumption across thousands of simultaneous connections, accepting a modest throughput ceiling per connection in exchange for predictable total memory usage) — but it's worth being aware that setting these options disables autotuning for that socket entirely, meaning a fixed value chosen without the reasoning from section 2.2 in mind can just as easily reintroduce the exact window-limited throughput problem autotuning exists to avoid, on a connection whose actual latency characteristics the fixed value doesn't happen to suit.

### 6.5 `TCP_QUICKACK` and delayed acknowledgments

Symmetrically to Nagle's algorithm (section 6.1) delaying small *outbound* segments, TCP also, by default, delays sending *acknowledgments* briefly (the **delayed ACK** mechanism), in hopes of piggybacking the acknowledgment on a data segment the receiver is about to send anyway (common in interactive, bidirectional protocols), or coalescing what would otherwise be several small acknowledgments into fewer, larger ones. This interacts with Nagle's algorithm in a specific, historically troublesome way worth knowing about: if both endpoints of a connection are running Nagle's algorithm and delayed ACKs simultaneously, a sender waiting to coalesce a small write with data acknowledgment can end up waiting on a receiver that's itself delaying that very acknowledgment, producing a measurable, if usually small, added latency neither side intended — a genuinely real interaction effect, not a hypothetical one, which is part of why `TCP_NODELAY` (disabling Nagle's algorithm on the sending side) is such a common recommendation specifically for latency-sensitive request/response protocols, sidestepping this interaction entirely from that side. `TCP_QUICKACK` addresses the same interaction from the receiving side, requesting that delayed acknowledgments be disabled (or, on Linux's particular implementation, disabled only until the next event that would naturally re-enable them, since the option isn't sticky in the way `TCP_NODELAY` is) — a less commonly reached-for option than `TCP_NODELAY`, but worth knowing exists for the cases where the receiving side, rather than the sending side, needs latency-sensitive behavior specifically around acknowledgment timing.

## 8. Glossary of terms introduced in this chapter

- **send/receive queue** — the bounded, per-socket buffers holding unacknowledged outbound data and unconsumed inbound data respectively (section 2).
- **receive window** — the amount of buffer space a receiver advertises as available, directly limiting how much unacknowledged data a sender may have in flight (section 2.2).
- **window scaling** — a negotiated TCP option extending the receive window beyond its native 16-bit range, needed for high-bandwidth, high-latency paths (section 2.2).
- **RTO (retransmission timeout)** — the adaptively-calculated timer governing how long TCP waits before assuming a segment was lost and retransmitting (section 3.2).
- **SRTT (smoothed round-trip time)** — the exponentially-weighted moving average of observed round-trip times, feeding directly into the RTO calculation (section 3.2).
- **fast retransmit** — recovering from an isolated lost segment via duplicate acknowledgments, without waiting for the RTO timer (section 3.3).
- **congestion window (cwnd)** — the sender-side window limiting in-flight data based on inferred network capacity, distinct from and generally smaller-or-equal to the receive window (section 4).
- **`ssthresh`** — the slow-start threshold, a remembered congestion-window value from a previous loss event, marking where slow start's exponential growth hands off to congestion avoidance's more conservative growth (sections 4.2–4.3).
- **slow start / congestion avoidance** — the two-phase growth pattern of the congestion window: rapid exponential growth followed by conservative, cautious growth once near a previously-known capacity limit (sections 4.2–4.3).
- **CUBIC / BBR** — two philosophically different congestion-control algorithms: loss-reactive (CUBIC) versus model-based on measured bandwidth and RTT (BBR) (section 4.4).
- **ECN (Explicit Congestion Notification)** — a mechanism letting routers signal incipient congestion by marking a packet rather than dropping it (section 4.5).
- **Nagle's algorithm / `TCP_NODELAY`** — the default small-segment-coalescing behavior, and the socket option disabling it for latency-sensitive applications (section 6.1).
- **`SO_REUSEPORT`** — the option allowing multiple sockets to share one listening address/port, load-balanced by the kernel (section 6.2).
- **`SO_LINGER`** — the option controlling whether `close()` blocks for pending data, and, with a zero timeout, forcing an abrupt RST-based teardown instead of a graceful close (section 6.3).
- **delayed ACK / `TCP_QUICKACK`** — the default acknowledgment-coalescing behavior on the receiving side, and the option requesting it be disabled (section 6.5).

## 9. A closing note connecting this back to chapters 1 through 4

Chapter 1 introduced TCP's named states and UDP's connectionless nature as observable facts; this chapter has, hopefully, supplied the mechanism behind both. The send and receive buffers from section 2 are the concrete kernel state that chapter 1's `read()`/`write()` calls actually operate on; the retransmission and congestion-control machinery from sections 3 and 4 are what turn IP's best-effort delivery (chapter 3) into TCP's reliable byte stream, entirely by a sender adaptively deciding how much to trust the network and how long to wait before assuming loss; and UDP's deliberate absence of all of this (section 5) is what makes it the right choice for applications that value timeliness over TCP's brand of reliability. Chapter 4's NAT and connection-tracking machinery, discussed there as sitting *below* this chapter's transport-layer state, now has its full counterpart *above* it visible as well — a NAT'd connection's conntrack entry and a TCP connection's own internal state machine are two separate, if related, pieces of bookkeeping, tracking overlapping but distinct information about the same logical connection.

It's worth drawing out one thread that has run through this entire chapter, because it's easy to lose sight of amid the individual mechanisms: almost everything described here — the RTO calculation, the congestion window, autotuned buffer sizes — exists because TCP has no advance knowledge of the network path it's running over, and has to *learn* that path's characteristics continuously, from measurements, while simultaneously trying to use it as effectively as possible without overwhelming it. This is a genuinely different design problem from anything in chapters 2 through 4, which were largely concerned with correctly executing decisions based on *already-known* configuration (a routing table, a firewall ruleset). TCP's transport-layer behavior is, by contrast, adaptive control under uncertainty — which is precisely why its behavior on any given connection reflects that connection's actual, specific history of measured round-trip times and observed loss, rather than being a fixed, predictable function of configuration alone. Recognizing this distinction is often the difference between correctly diagnosing a transport-layer performance question (checking `ss -tin` for the actual RTT, congestion window, and algorithm in use, as section 2.2 demonstrated) and mistakenly looking for a configuration error where none exists — the "problem," if there is one, may simply be TCP correctly adapting to network conditions that are themselves the actual root cause.

Chapter 6 turns to a layer above all of this: DNS, the mechanism by which most connections' destination addresses get determined in the first place, before any of this chapter's machinery ever has a segment to send.
