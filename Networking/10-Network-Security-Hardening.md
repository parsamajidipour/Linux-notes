# Chapter 10: Network Security Hardening

## 1. What this chapter is actually for

Every previous chapter described a mechanism as it ordinarily behaves. This chapter takes a specific subset of that behavior — the sysctl-level knobs governing how the kernel's networking stack responds to adversarial or malformed traffic — and examines each one for what it actually defends against, and what accepting it costs. This is deliberately not a checklist of settings to enable uniformly; several of the settings this chapter covers involve genuine tradeoffs, and applying them without understanding the tradeoff is exactly the kind of cargo-culted configuration chapter 2's introduction warned against in a different context.

It's worth being explicit about the kind of security this chapter covers, because "network security" spans a wide range of concerns, most of which are out of scope here. This chapter is about kernel-level hardening — sysctl settings that change how the networking stack itself responds to specific classes of traffic, mostly at or below the layers chapters 2 through 5 described. It is not about application-layer security (TLS configuration, authentication schemes), not about the cryptographic protocols chapter 8 already covered, and not about Netfilter rule design beyond what chapter 4 already established — this chapter's subject is narrower and more specific: the defensive sysctls sitting underneath all of that, in the kernel's own protocol implementations.

It's worth naming, up front, why this chapter treats every setting as a tradeoff rather than a straightforward improvement, since that framing runs through the entire chapter and is easy to lose sight of when reading any single section in isolation. Security hardening, at the kernel level, is rarely a matter of finding purely beneficial settings with no offsetting cost — if such settings existed with no downside at all, they would simply be the kernel's unconditional default behavior, not an optional, separately-documented sysctl an administrator has to deliberately enable. The fact that a setting exists as a toggle, rather than as fixed, non-configurable behavior, is itself usually evidence that reasonable systems genuinely differ on whether its cost is worth its benefit — a distinction worth holding onto through the more specific examples that follow, several of which will make this tradeoff structure concrete rather than abstract.

## 2. SYN cookies: surviving a SYN flood without giving up state

Chapter 1's section 8 described the TCP handshake's `SYN_RECV` state — the brief window between receiving a SYN and completing the handshake with the client's final ACK. A **SYN flood** attack exploits this window directly: an attacker sends a large volume of SYN segments, typically with spoofed source addresses, never completing any of the resulting handshakes, with the specific goal of exhausting the server's backlog of half-open `SYN_RECV` connections — since each half-open connection consumes kernel memory to track (chapter 5, section 2's socket buffer model applies even to this incomplete state, since the kernel must remember enough about the connection attempt to process the eventual ACK, should it ever arrive), a sufficiently large flood can exhaust that backlog entirely, causing the server to drop legitimate SYN segments from real clients simply because no room remains to track them.

### 2.1 The naive defenses, and why they're insufficient alone

A naive first response is simply increasing the backlog size (`net.ipv4.tcp_max_syn_backlog`) — genuinely helpful up to a point, but not a real solution, since it only raises the bar an attacker's flood needs to clear, not close off the underlying vulnerability; a sufficiently large flood still exhausts a sufficiently large backlog, merely requiring more attacking traffic to do so. A second naive approach, reducing the SYN-ACK retransmission timeout so half-open connections are abandoned faster (freeing backlog slots more quickly), helps marginally but similarly doesn't address the core problem: the kernel is still required to allocate and track state for every SYN it decides to respond to, before knowing whether the sender will ever complete the handshake at all.

### 2.2 SYN cookies: not tracking the connection at all until it's confirmed real

**SYN cookies** (`net.ipv4.tcp_syncookies`) solve this more fundamentally, by changing what the server actually does upon receiving a SYN, once the backlog is under pressure: rather than allocating real connection state and remembering it, the server encodes the essential connection parameters (roughly, a hash of the source/destination address and port, a timestamp, and the negotiated maximum segment size) directly into the sequence number of its SYN-ACK reply, and then forgets about the connection attempt entirely — no backlog slot consumed, no memory held. If and when the client's final ACK arrives, its acknowledgment number (which, per ordinary TCP mechanics, reflects the server's chosen sequence number, incremented by one) lets the server *reconstruct* the original connection parameters directly from that number, without ever having stored them — and only at that point, once a genuine, completed handshake is confirmed, does the server allocate the real connection state chapter 5 described.

This is a genuinely elegant solution to the SYN-flood problem specifically because it inverts the vulnerable assumption: rather than "remember every half-open attempt, hope legitimate ones complete before an attacker's flood exhausts the memory," it becomes "remember nothing until a connection proves itself genuine by completing the handshake," which an attacker spoofing source addresses and never intending to complete anything simply cannot do, regardless of how much SYN traffic they generate. The approach isn't free of cost, though it's a comparatively minor one worth naming precisely: encoding connection parameters into 32 bits of sequence number space necessarily loses some information relative to genuinely-stored state — certain TCP options (some forms of window scaling, in particular) can't be fully preserved through the cookie encoding, meaning a connection established via a SYN cookie can, in some configurations, negotiate slightly less optimal parameters than one established through the ordinary, fully-stateful path. This is precisely why Linux enables SYN cookies as a *fallback*, triggered specifically once the backlog is genuinely under pressure, rather than using them unconditionally for every connection — the ordinary case, with no attack in progress, gets the fully-stateful, no-compromise handshake path, and cookies activate only as a defensive measure exactly when needed.

## 3. `rp_filter`: rejecting traffic that couldn't have arrived honestly

**Reverse path filtering** (`net.ipv4.conf.*.rp_filter`) addresses a different class of problem: spoofed source addresses used not to exhaust backlog (section 2) but to disguise where traffic is genuinely coming from, or to redirect a reply toward an unwitting third party (the basis of reflection/amplification attacks, where a small spoofed request triggers a much larger reply directed at the spoofed, victim address rather than the actual sender).

### 3.1 The check itself: would a reply to this source be routed back out this same interface?

The mechanism is straightforward given chapter 3's routing model: for a packet arriving on a given interface, `rp_filter` checks whether the kernel's own routing table (chapter 3, section 3) would select that *same* interface as the outbound path for a reply to the packet's claimed source address. If the answer is no — if this specific packet's claimed source address would, according to the routing table, be reached via a *different* interface — the packet is treated as suspicious and dropped, on the reasoning that an honest packet from that source genuinely should have arrived via the interface routing considers appropriate for reaching it, and one that didn't is more likely to be spoofed than to reflect a legitimate, if unusual, routing asymmetry.

### 3.2 The genuine tradeoff: asymmetric routing breaks this check legitimately

This is precisely where the tradeoff chapter 1's abstract mention of `rp_filter` deferred becomes concrete: the check's underlying assumption — that legitimate traffic arrives via the same path a reply would take — is not universally true. A machine with genuinely asymmetric routing (traffic to a destination goes out one path, but replies from that destination legitimately arrive via a different path, a real and not uncommon topology in some multi-homed or BGP-influenced network designs) will have entirely legitimate traffic rejected by strict `rp_filter` enforcement, precisely because that traffic's arrival pattern looks, by this check's logic, identical to spoofed traffic. This is exactly why `rp_filter` supports a "loose" mode (value `2`, as opposed to strict mode's value `1`) alongside strict enforcement: loose mode only checks whether *some* route exists back to the claimed source address via *some* interface, rather than requiring it be specifically the interface the packet actually arrived on — a meaningfully weaker check, but one that still rejects packets with genuinely bogus, unroutable source addresses (the core reflection/spoofing concern) while tolerating legitimate asymmetric-routing topologies that strict mode would incorrectly reject.

### 3.3 Per-interface configuration and the `all`/`default` distinction

It's worth flagging a configuration detail that trips people up when first applying `rp_filter` or the other `net.ipv4.conf.*` settings this chapter covers: these settings exist per-interface (`net.ipv4.conf.eth0.rp_filter`, for instance), plus two special pseudo-interfaces, `all` and `default`. The actual enforced behavior for a given real interface is effectively the *stricter* (numerically higher, in `rp_filter`'s case) of that interface's own specific setting and the `all` pseudo-interface's setting — meaning setting `net.ipv4.conf.all.rp_filter = 1` doesn't necessarily mean every interface enforces strict filtering if some specific interface has its own, more permissive value configured; conversely, a specific interface's stricter setting isn't relaxed by a laxer `all` value. `default`, distinctly, only affects interfaces created *after* it's set — it has no effect on already-existing interfaces at all. This distinction matters concretely for anyone scripting interface creation or troubleshooting an rp_filter-related drop that persists despite `all` apparently being configured correctly: the actual, effective setting for the specific interface in question needs checking directly, not inferred from the `all` value alone.

## 4. SYN-ACK and ICMP rate limiting: throttling rather than blocking outright



Beyond SYN cookies specifically, the kernel maintains several rate limits on how quickly it will emit certain kinds of response traffic, worth understanding as a distinct category from the outright accept/reject decisions sections 2 and 3 covered.

### 4.1 ICMP rate limiting and its role in mitigating reconnaissance and reflection

`net.ipv4.icmp_ratelimit` (and related settings governing which specific ICMP message types are subject to it) caps how frequently the kernel will emit ICMP error messages (destination unreachable, time exceeded — the exact messages chapter 3's `traceroute` discussion, section 6.2, depended on) in response to unwanted or malformed traffic. This serves two distinct defensive purposes worth separating clearly: first, it limits the effectiveness of network reconnaissance techniques that rely on eliciting many ICMP responses in quick succession to map a network's structure or discover live hosts; second, and more directly relevant to modern attack patterns, it limits a machine's usefulness as an unwitting participant in a reflection attack, where an attacker sends traffic designed to elicit an ICMP reply directed at a spoofed victim address — rate-limiting the replies directly caps how much amplification traffic any single machine can be tricked into generating on an attacker's behalf, regardless of how much triggering traffic the attacker sends.

### 4.2 The cost: legitimate diagnostic traffic can be affected too

The same rate limit that throttles an attacker's ability to elicit ICMP responses also throttles legitimate diagnostic tools relying on the same mechanism — an aggressive `traceroute` or path-MTU-discovery process (chapter 8, section 5.2's discussion of Path MTU Discovery depends directly on ICMP "fragmentation needed" messages not being suppressed) run against a machine with strict ICMP rate limiting configured can itself be affected, seeing gaps or delays in responses that have nothing to do with actual network conditions and everything to do with the rate limit itself. This is a genuine instance of the broader hardening-versus-diagnosability tension this chapter keeps surfacing: a setting that correctly defends against abuse of a mechanism necessarily also constrains legitimate use of that same mechanism, since the kernel has no way to distinguish, at the point of deciding whether to respond, between a legitimate diagnostic tool and an attacker abusing the identical protocol feature.

### 4.3 A worked contrast: two machines, two correct answers

It's worth making section 4.2's tradeoff concrete with a direct comparison, since "the right value depends on context" is easy to accept in the abstract while still leaving unclear what the actual decision-making looks like in practice. A public-facing DNS resolver, expected to handle high query volumes from many, mostly-unknown clients, has good reason to keep ICMP rate limiting conservative — the diagnostic cost (a client's own path-MTU discovery or traceroute being marginally throttled) is a cost borne by that client, not by the resolver itself, while the security benefit (limiting the resolver's usefulness as a reflection-attack amplifier) protects the resolver's own operator and reputation directly. A machine used primarily for internal network diagnostics and troubleshooting — a jump host or monitoring server whose main traffic pattern *is* diagnostic probing of other internal machines — has the opposite balance of interests: aggressive ICMP rate limiting on such a machine directly degrades the very function it exists to perform, while the reflection-attack risk it's nominally defending against is considerably less relevant for a machine that isn't internet-facing at all, or sits behind other defenses already. Neither machine's correct setting generalizes to the other, and recognizing which situation a specific machine actually resembles — public-facing and high-volume, or internal and diagnostic-heavy — is precisely the judgment this chapter's tradeoff framing is meant to support, rather than either machine simply adopting whatever value happens to be the more commonly recommended default elsewhere.

## 5. TCP-specific hardening: sequence numbers, timestamps, and RST behavior



A handful of TCP-specific settings address narrower, more specific attack classes worth naming individually, since each defends against a genuinely distinct threat model.

### 5.1 Sequence number randomization and why it matters beyond ordinary operation

Chapter 5's section 3 described sequence numbers primarily as a mechanism for detecting loss and reordering, without dwelling on their security role. A predictable initial sequence number — one derivable or guessable by an off-path attacker who isn't actually positioned to observe the real traffic between two endpoints — historically enabled a class of attack where that attacker could inject forged segments into an existing connection, or even establish an entirely spoofed connection, without ever needing to see the genuine traffic at all, purely by guessing what sequence number the real connection would be using at a given moment. Modern Linux kernels randomize initial sequence numbers strongly enough that this specific attack is no longer practical against a correctly-configured system — this is, at this point, a settled, non-configurable baseline rather than an optional hardening toggle, worth mentioning here mainly because understanding *why* sequence numbers need to be unpredictable (a security property) rather than merely well-distributed (a performance/collision-avoidance property, the concern chapter 5's own treatment focused on) fills in a gap that chapter's transport-layer-focused treatment didn't need to address.

### 5.2 TCP timestamps and the tradeoff between RTT precision and information disclosure

`net.ipv4.tcp_timestamps`, enabling the TCP timestamp option chapter 5 didn't cover in detail, improves round-trip-time measurement precision (directly feeding into the RTO calculation, chapter 5 section 3.2) and enables PAWS (Protection Against Wrapped Sequence numbers, a mechanism helping very-high-bandwidth connections avoid a specific sequence-number-wraparound ambiguity). The security-relevant cost, worth naming plainly: a machine's TCP timestamp value, observed across multiple connections, can in principle be used to estimate that machine's system uptime, and, in some circumstances, to help distinguish or fingerprint distinct machines sitting behind a shared, NAT'd address (chapter 4's `MASQUERADE`, section 4.2) by their differing timestamp clock behavior — a genuine, if narrow, information-disclosure concern that has led some security-conscious deployments to disable timestamps despite the RTT-precision and PAWS benefits given up in exchange. This is a clear instance of the tradeoff structure this chapter keeps returning to: a setting that measurably helps ordinary operation (better RTT estimates, safer sequence-number handling at high bandwidth) also measurably assists an adversary in a specific, narrow way, and the right choice depends on which side of that tradeoff matters more for a given deployment's actual threat model.

### 5.3 RST behavior and the `tcp_rfc1337` mitigation

Chapter 1's section 8 mentioned `RST` only in passing (as part of the connection-teardown discussion in chapter 5, section 6.3, regarding `SO_LINGER`). It's worth knowing that RST handling has its own, narrower hardening consideration: `net.ipv4.tcp_rfc1337`, when enabled, changes how the kernel handles a RST received while a connection is in the `TIME_WAIT` state (chapter 1, section 8) — instead of accepting a RST during `TIME_WAIT` and thereby ending that waiting period early (the older, more permissive behavior, which can in principle be exploited to prematurely terminate a `TIME_WAIT` state that was, per its original purpose described in chapter 1, deliberately protecting against delayed-duplicate-segment confusion), the RFC 1337-compliant behavior simply ignores such a RST, letting the `TIME_WAIT` period run its full, intended course regardless. This is a narrow, low-cost hardening setting — unlike sections 2 through 5.2's genuine tradeoffs, there's little legitimate use case that depends on being able to prematurely end a `TIME_WAIT` period via an unsolicited RST, making this one of the more unambiguously beneficial settings this chapter covers.

## 6. IP-level hardening: source routing, redirects, and martian packets

A further cluster of settings governs how the kernel handles specific IP-layer features and anomalies, several of which exist for legitimate historical reasons but carry security implications significant enough that disabling them is standard practice on hardened systems.

### 6.1 Source routing: a legacy feature with little legitimate remaining use

IP source routing — a now-obscure header option letting the *sender* of a packet specify the exact route it should take through the network, rather than leaving that decision to ordinary routing (chapter 3) at each hop — was a genuinely useful diagnostic and routing-override tool in IP's earliest days, but has essentially no legitimate use in a modern network, while offering a real attack vector: a sender could use source routing to make traffic appear to originate from, or route through, a location it doesn't actually occupy, or to route around security devices that assume ordinary routing behavior. `net.ipv4.conf.*.accept_source_route` (disabled by default on modern kernels, and left disabled on any reasonably hardened system) governs whether the kernel honors this option at all — this is a case where the tradeoff section 5.2 illustrated barely applies, since there's essentially no legitimate contemporary use case being sacrificed by disabling it.

### 6.2 ICMP redirects: legitimate on some networks, a spoofing vector on others

An **ICMP redirect** message is a router's way of telling a host "you sent this packet to me, but a different, more direct next hop would have been better — use that one from now on for this destination" — a legitimate optimization mechanism in some network topologies, letting hosts with a suboptimal or overly simple routing table (chapter 3) learn better routes dynamically rather than requiring administrator intervention. The security concern is direct: an attacker positioned to send a host a forged ICMP redirect can potentially redirect that host's traffic toward an attacker-controlled next hop instead, a legitimate-looking mechanism used illegitimately. `net.ipv4.conf.*.accept_redirects` governs whether a host honors these messages at all, and the tradeoff here is genuinely dependent on network topology and role: a host that's itself acting as a router, forwarding traffic for others, should virtually always have this disabled (an actual router should be relying on its own configured or dynamically-learned routing table, chapter 3, not accepting redirects that could originate from a compromised or malicious peer), while an ordinary end-host on a simple, well-controlled internal network might reasonably accept redirects from a trusted, adjacent router without meaningful risk — the setting's correct value is a function of the host's role and the trustworthiness of its local network segment, not a universal on/off choice.

### 6.3 Martian packet logging and filtering

A **martian packet** — the term's origin is informal but the concept is precise — is a packet whose source or destination address is invalid or nonsensical given the interface it arrived on or the kernel's own address configuration: a packet claiming a source address from a private range (chapter 3's addressing discussion) arriving on a public-facing interface, or a packet destined for an address that couldn't plausibly be reached via the arriving path at all. `net.ipv4.conf.*.log_martians` enables logging these occurrences specifically, and it's worth understanding this as a detection/visibility tool rather than a preventive one in its own right — many martian packets are already implicitly rejected by `rp_filter` (section 3) or ordinary routing logic before ever reaching the point this logging would fire, but enabling the logging specifically surfaces the *attempt*, which can be valuable evidence of scanning, spoofing attempts, or misconfiguration elsewhere on a network, distinct from `rp_filter`'s silent, un-logged rejection.

### 6.4 The bogon and unroutable-prefix problem, briefly

A related concept worth mentioning alongside martian packets: **bogon** filtering, the practice of dropping traffic claiming to originate from IP ranges that have never been allocated for legitimate use at all (certain reserved, unallocated address blocks) or that are allocated but not expected to appear on this specific network's path. Unlike `rp_filter`, which checks a claimed source address against *this machine's own* routing table, bogon filtering typically requires an externally-maintained, periodically-updated list of currently-unallocated or reserved ranges, since address allocation changes over time as previously-reserved blocks get assigned for real use — a static, hardcoded bogon list becomes stale and can begin incorrectly rejecting legitimate traffic from a range that was reserved when the list was created but has since been allocated. This is mentioned here mainly to distinguish it clearly from `rp_filter` and martian-packet detection: those two are genuinely local, self-contained mechanisms based entirely on this machine's own configuration and routing table, requiring no external data feed at all, while effective bogon filtering is inherently a maintenance burden requiring ongoing external data — a meaningfully different operational commitment than simply enabling a sysctl once and leaving it alone.

## 7. A worked example: composing several settings for a specific threat model



It's worth pulling several of this chapter's settings together into a concrete scenario, since the individual pieces are more useful seen composed than in isolation. Consider a public-facing web server, directly exposed to the internet, with no legitimate reason to expect asymmetric routing, redirects from trusted routers, or source-routed traffic:

```
net.ipv4.tcp_syncookies = 1
net.ipv4.conf.all.rp_filter = 1
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.log_martians = 1
net.ipv4.icmp_ratelimit = 100
```

Each line here maps to a specific threat this section has already named individually: SYN cookies (section 2) defending backlog exhaustion; strict `rp_filter` (section 3) rejecting spoofed-source traffic, justified here specifically because this server's simple, single-homed topology makes asymmetric routing genuinely unlikely, unlike the multi-homed case section 3.2 flagged as needing loose mode instead; disabled source routing and redirects (sections 6.1, 6.2), appropriate for an end-host rather than a router, with no trusted adjacent router whose redirects would be worth honoring; martian logging (section 6.3) providing visibility into scanning or spoofing attempts; and a conservative ICMP rate limit (section 4) capping this machine's usefulness as a reflection-attack amplifier, at some acknowledged cost to legitimate diagnostic traffic's own responsiveness. No single setting here is doing anything mysterious — the value of walking through them together is seeing how a coherent hardening posture is genuinely just this chapter's individual mechanisms, each selected and configured based on an accurate understanding of this specific machine's actual role and network topology, rather than applied as an undifferentiated, one-size-fits-all checklist.

## 8. What's deliberately being deferred

- IPv6-specific hardening equivalents (many of the settings this chapter covered have IPv6 counterparts under `net.ipv6.conf.*`, with some behaving subtly differently given IPv6's different addressing and neighbor-discovery model, chapter 3's section 11) are not covered individually here, though the underlying principles — understand the threat, understand the tradeoff — apply identically.
- DDoS mitigation at scale (traffic scrubbing, upstream filtering, anycast-based absorption) operates at a scale and layer beyond single-machine sysctl configuration, and is a distinct, considerably larger operational subject not covered in this series.
- Application-layer security (TLS configuration, certificate validation, authentication schemes) sits above everything this series has covered and is deliberately out of scope, as flagged in section 1.
- Netfilter rule design for security purposes beyond what chapter 4 already covered (rate-limiting connection attempts via `hashlimit`, more elaborate DDoS-mitigation rule patterns) is a natural extension of chapter 4's material this chapter doesn't repeat.

## 9. Glossary of terms introduced in this chapter

- **SYN flood** — an attack exhausting a server's half-open-connection backlog by sending many SYN segments, typically with spoofed sources, without ever completing the handshake (section 2).
- **SYN cookies** — a defense encoding connection parameters into the SYN-ACK sequence number itself, avoiding the need to store state for unconfirmed connection attempts (section 2.2).
- **reverse path filtering (`rp_filter`)** — a check rejecting a packet if the routing table wouldn't route a reply to its claimed source back out the interface it arrived on, with strict and loose enforcement modes (section 3).
- **`all` / `default` pseudo-interfaces** — the two special entries alongside real per-interface `net.ipv4.conf.*` settings, combining with an interface's own value (typically to the stricter of the two) or governing only newly-created interfaces, respectively (section 3.3).
- **reflection/amplification attack** — an attack pattern using spoofed source addresses to redirect a (typically larger) response toward an unwitting victim rather than the actual sender (sections 3, 4.1).
- **ICMP rate limiting** — throttling how frequently the kernel emits ICMP responses, limiting both reconnaissance and reflection-attack amplification at the cost of some legitimate diagnostic responsiveness (section 4).
- **IP source routing** — a legacy IP header option letting a sender dictate a packet's exact path, with essentially no legitimate modern use and a real spoofing/routing-bypass risk (section 6.1).
- **ICMP redirect** — a router-originated message suggesting a better next hop for a given destination, legitimate on some trusted topologies but a spoofing vector when accepted from an untrusted or unexpected source (section 6.2).
- **martian packet** — a packet whose source or destination address is invalid or implausible given its arrival interface or the local address configuration (section 6.3).

## 10. A closing note connecting this back to the rest of the series

Every setting this chapter has covered modifies the behavior of a mechanism some earlier chapter already described in its ordinary, undefended form: SYN cookies alter chapter 1 and chapter 5's handshake handling specifically under backlog pressure; `rp_filter` applies chapter 3's own routing table as a check against incoming traffic's plausibility, rather than only using it to decide outgoing traffic's path; ICMP rate limiting throttles exactly the diagnostic mechanism chapter 3's `traceroute` discussion and chapter 8's Path MTU Discovery both depend on, illustrating directly how a defensive measure and a legitimate diagnostic tool can draw on the identical underlying protocol feature; and source-routing and redirect handling govern edge-case IP-header features chapters 1 through 3 didn't need to dwell on because they're rare enough in ordinary operation to not matter for understanding routing's normal case, while mattering considerably for understanding routing's adversarial case.

The throughline worth taking from this chapter, more than any individual setting, is the tradeoff structure itself: essentially every setting here trades something — some legitimate capability, some diagnostic visibility, some rare-but-real use case — for a security benefit, and almost none of them are correct choices in every context, independent of a specific machine's actual role and threat model. Chapter 11, the final chapter in this series, turns to troubleshooting in full — a systematic method for diagnosing network problems that draws on every mechanism this entire series has built, including, where relevant, recognizing when a hardening setting from this very chapter is itself the actual cause of an otherwise-puzzling symptom, rather than assuming every problem must originate somewhere else in the stack.
